# TODO 的含义、例子与完成标准

更新：2026-10-07，America/Phoenix。对应 [当前功能与剩余工作](REMAINING_WORK.md)。当前版本为 **0.0.7 / API 1.2.0 / profile v4**，两平台原生 CI、合成扫描和安装检查已通过；下面写的是还要做的事，不是新增功能已交付的声明。

“已实现”指代码具备能力；“CI 通过”指特定提交在受控 runner/合成输入通过验证；“真机通过”还需要实际桌面、系统电源事件和真实安装/升级操作。三种证据不能互相替代。

<a id="t1"></a>
## T1：真实桌面 UI/IPC 验收

**含义：** 安装当前包并使用真实 Tauri 窗口，确认按钮、原生目录/保存对话框、Rust 命令、SQLite 和采集器确实协同工作。浏览器 Mock 不读磁盘；native fixture 直接调用后端，都不能证明实际 WebView 的完整操作链路。

**例子：** 在 Windows 选择带中文/空格的合成日志目录，启用 Claude Code，点击扫描，看到图表和会话更新，再保存 CSV；在 macOS 用相同步骤验证 WKWebView。切到英文后，窗口标题、提示和操作结果应一起改变，已选来源和统计时区保持。

**完成标准：** 两平台分别记录包 SHA、OS、WebView/运行环境、步骤和结果；覆盖启用/关闭、目录取消、设置冲突、手动/自动任务取消、缓存更新、导出取消/保存、关闭/重启与单实例行为。发现问题修复后回归。可先用合成日志；真实数据验证只在本机进行，证据脱敏。

<a id="t2"></a>
## T2：自动扫描的真实运行与休眠恢复

**含义：** 已有恢复检测和可控时间测试，还要确认系统真的睡眠后，其计时器、文件监听、WAL、WebView 和子进程行为符合预期。

**例子：** 开启 1 分钟自动采集后最小化，向合成 JSONL 追加 usage；睡眠跨过三个周期再唤醒。应合并为一次检查，而不是补跑三个任务。持续写入不能每 2 秒启动一个完整扫描；扫描中又有变化应在后续合适轮次采到。

**完成标准：** Windows 与 macOS 分别实测最小化、睡眠/恢复、连续写入、历史修正、DB WAL、监听故障后备、失败/取消保留历史；关闭开关只停止自动工作，用户任务不被误取消；退出后主程序/sidecar 无残留。记录 job ID、时间和结果，不能用模拟时间证明硬件睡眠通过。

<a id="t3"></a>
## T3：安装、升级、干净机和最低系统版本

**含义：** CI 已经实际安装 NSIS、解压 ZIP、挂载复制 DMG，但 runner 有开发工具和系统组件，不能代表所有普通电脑。用户从老版本升级也与全新安装不同。

**例子：** 先使用 0.0.6 产生历史并保存时区，再换成 0.0.7。升级后应保留 deviceId/datasetId、统计历史和该版本适用的时区迁移结果，自动采集仍默认关闭。便携版与安装版共用用户数据目录，要验证它们不会创建第二份身份或互相写坏数据。

**完成标准：** 用数据副本验证升级，检查身份、配置、历史和旧进程退出；测试无额外 Node/Rust/ccusage 的机器、缺少 WebView2 时的安装引导、便携版要求、卸载是否保留数据、下载后 macOS 隔离属性/Gatekeeper 场景。根据实际测试声明最低 Windows/macOS 版本；构建目标 macOS 13.0 不等于已在 13.0 实测。profile v4 不保证旧宿主可读，不能宣传无条件降级。

<a id="t4"></a>
## T4：长期下载入口和版本化发布

**含义：** 现在安装包在 Actions artifacts 中，只保留一天，并需要登录下载。README 的 Daily build 是开发构建入口，尚不是自动替换附件的滚动 Release。

**计划行为：** 开发渠道提供最新成功代码的包，允许按明确规则更新；固定版本（例如 v0.0.7）提供对应提交的固定安装包与 SHA，供复现、长期使用和包管理器引用。失败构建不替换最后一个成功包；只在两平台及汇总门槛通过后更新渠道。

**完成标准：** 明确滚动渠道、固定 tag/Release、资产命名/保留和重试规则，绑定准确代码提交，提供两个系统的包和校验材料，验证首次发布与重复执行。固定附件“不变”需要流程或平台机制约束，不能仅凭一个版本 tag 就承诺附件不可替换。[GitHub Release 管理](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository) · [Release 不可变机制](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/establish-provenance-and-integrity/prevent-release-changes)

滚动更新策略不能与其所用 Release 的不可变约束冲突；方案落实前不创建假下载链接，不覆盖已有源码预览 tag/Release。此次文档整理不等于授权实际发布。

<a id="t5"></a>
## T5：Windows 正式签名与 macOS 公证

**含义：** SHA-256 说明文件是否与已知文件一致；发布者签名用于验证软件来源与字节完整性。当前 Windows 包未签名，Mac 主程序/.app 为 ad-hoc，尚未配置正式发布身份。

**Windows：** 为发行文件建立 Authenticode 签名与时间戳流程，验证签名者、证书链和实际产物。时间戳是签名流程中的另一项验证，不能承诺签名后所有 SmartScreen 提示都会立即消失。[Microsoft Authenticode 与时间戳](https://learn.microsoft.com/en-us/windows/win32/seccrypto/time-stamping-authenticode-signatures)

**macOS：** Developer ID 为 App Store 外分发提供开发者身份；公证是向 Apple 提交软件进行检查并取得公证票据。要验证主程序、嵌套 sidecar、app/DMG 与实际下载后的 Gatekeeper 行为。[Apple Developer ID](https://developer.apple.com/developer-id/) · [Apple 公证说明](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)

**完成标准：** 凭据存储/权限与发布流程经过批准，包内签名与安装后的验证成功，签名失败不能发布为正式签名包。本项目还需处理重签 sidecar 可能改变原始 SHA 的信任关系，不能简单关闭原始来源校验或信任现场新算的 hash。平台证书、公证、SHA、应用更新签名用途不同；账号/证书/密钥操作另行授权。未正式签名不妨碍继续做明确标识的内部测试。

<a id="t6"></a>
## T6：完整第三方依赖许可清单

**含义：** 已打包 ccusage 的完整 MIT 文本，不代表已完成整个产品的依赖清单。前端打包代码、Rust/native 链接代码及随包二进制还来自其他依赖。

**例子：** 清单需区分随产品交付的 React/TanStack Query、Rust/Tauri/native 库和仅用于构建/测试的工具，记录版本、来源、许可及需要保留的声明；不能把“所有包都是开源”当成审查完成。

**完成标准：** 基于锁文件和实际包内容生成库存，人工核对分发要求与缺失/冲突信息，将需要随包交付的 notices 纳入安装版、便携版、DMG 并验证；依赖升级时更新清单。自动 license 字段只能作为材料，不代替逐项核对。本 TODO 是工程库存与发布准备，不是对许可适用性的法律结论。

<a id="t7"></a>
## T7：真正增量采集

**含义：** 当前流程是“轻量检查变化→现有完整扫描→完整快照替换”。增量需要只读取/解析新增或被修正的部分，并最终得到与完整扫描相同的统计。

**例子：** 某个 1 GB 日志只追加 10 KB，增量希望主要处理这 10 KB。但如果旧行被修正、文件截断/替换，或者来源报告累计计数后又 reset，仅保存最后字节位置再累加会漏数据或重复统计。

**完成标准：** 每个来源分别定义文件/事件身份、游标版本、轮转/截断/修正/累计 reset、失败恢复和事务规则；保证重复执行、退出重启及修正与完整扫描一致，保留周期性全量复核/回退。JSONL 与 SQLite/WAL 的实现方案可能不同；现有 metadata 指纹和文件监听不是增量解析，三个 supportsIncrementalCollection 目前仍为 false。

<a id="t8"></a>
## T8：备份、恢复、清除与应用数据目录迁移

**含义：** 给普通用户提供维护 profile.json、usage.db、身份与相关状态的操作。底层 SQLite 已有备份/恢复相关测试，用户可操作的完整维护流程尚未提供；现有 JSON 导出也不是完整应用备份。

**例子：** 换电脑前备份，恢复后沿用同一份身份和历史；数据库损坏时恢复最后好备份；清除前先展示会删除什么。“更换来源日志目录”改变读取输入，“迁移应用数据目录”移动本软件的配置/数据库，二者不是同一件事。

**完成标准：** 活动扫描期间有门禁，一致备份、版本/身份校验、原子恢复与失败回滚；清除有范围预览/必要确认，迁移后数据库与配置一致。不能无提示重新生成身份，也不能把用户的原始日志当成本软件缓存一并删除。

<a id="t9"></a>
## T9：归档导入、多设备与独立数据集

**含义：** 目前可以导出完整归档，还不能从 UI 导入。多设备支持要区分真正不同的数据与同一份日志的副本；独立数据集需要明确选择和身份管理。

**例子：** 导入同一份归档两次，总数不应翻倍；同数据集有更新 revision 时应按规则替换旧快照；把同一份日志从笔记本复制到台式机，也不能仅凭两个 deviceId 就求和。现有目录选择只承诺同一日志迁移，不是“切换另一份独立数据集”。

**完成标准：** 校验归档 schema、指标/范围和身份，提供导入预览、幂等/revision/冲突处理及失败回滚，未知重叠明确提示。Daily 与 Session 本来也不能互相相加。联网同步是额外功能，归档导入/多设备管理不自动意味着云同步。

<a id="t10"></a>
## T10：系统时区变化自动跟随

**状态（2026-10-07）：** 本地实现已完成（应用 0.0.8 / API 1.3.0 / profile v5，分支 `feat/follow-system-timezone`），尚未运行两平台 CI，也没有新包或真机证据。[设计与本地验证](../ci-validation/follow-system-timezone-v1.md)

**含义：** 统计时区有两种持久模式：“跟随系统”（新配置默认）由 Rust 宿主检测系统 IANA 时区并在安全边界切换；“固定时区”使用用户选择的时区，系统变化只显示不应用。旧配置无法区分手动选择与旧默认，因此迁移为固定并保留原时区（包括明确的 UTC）。

**例子：** 跟随模式下系统从 Phoenix 改为 Tokyo：若正在扫描，界面显示待切换目标，扫描按 Phoenix 完成；随后切换为 Tokyo 并从原始日志重建已启用来源的 Tokyo Daily/Session 快照，Phoenix 快照保留。重建完成前 Tokyo 统计可能不完整，缺失数据显示为不可用。夏令时偏移变化、同一时区的旧拼写都不触发重建。语言或主题切换仍不影响统计时区和采集。

**剩余完成标准：** 现有 Windows/macOS CI 编译并通过新增 Rust 单元/集成测试、严格 clippy、`cargo fmt --check` 与跨午夜 native 重建测试，生成新包；两平台真机在运行中切换系统时区（前台焦点、后台轮询、睡眠后唤醒）、扫描中切换、快速连续切换、取消/失败后重试、重建中退出再启动、固定模式不跟随，以及 0.0.7 数据升级后保持固定模式；记录包 SHA、系统版本与结果。证据齐全前不把 T10 标为完成。

<a id="t11"></a>
## T11：自定义日期范围与项目统计

**含义：** 当前 UI 有今日、本周、本月、最近 30 天等预置范围；增加起止日期选择器主要是 UI/边界验收。后端已有日期查询不等于 UI 已提供任意日期选择。项目维度则还需要可信项目标识和契约/数据支持。

**例子：** 比较两次活动期间用量，或者查看同一工具在项目 A/B 的使用差异。项目不能只凭会话标题猜测；来源未提供时应显示未知，不把所有会话错误归给一个项目。

**完成标准：** 明确闭开日期边界与统计时区，Overview、会话活动日期筛选、分页、CSV 保持一致；会话仍展示累计量而非虚构期间消费。项目标识有出处、隐私处理、unknown 状态与按能力禁用，聚合总计不能重复计数。

<a id="t12"></a>
## T12：托盘、开机启动、通知和自动更新

这是四个分别开发和验收的功能，不是加一个开关即可一起完成：

| 功能 | 含义与完成标准 |
| --- | --- |
| 托盘 | 窗口关闭/隐藏后可继续在进程内工作，托盘可重新打开或真正退出；需明确“关窗口”和“退出”区别，退出仍回收 timer/watcher/sidecar。当前只有最小化继续工作 |
| 开机启动 | 用户独立选择在登录系统后启动；两平台注册/取消、单实例和卸载清理正确。启动不自动等于启用来源或自动采集 |
| 通知 | 在用户允许时提示有意义的成功/失败/需要操作，避免每轮检查刷通知，不泄露路径/正文；关闭通知不停止采集 |
| 自动更新 | 检查渠道、下载并验证对应架构更新包、重启安装和失败恢复；需要独立更新签名、版本/数据库迁移与降级策略。GitHub 有新构建不等于已具备 updater |

**完成标准：** 四项有各自生命周期、独立偏好和平台证据；系统自启动/通知权限与联网更新用途明确，签名/密钥和发布渠道另行授权。当前不增加常驻系统服务。

<a id="t13"></a>
## T13：Antigravity conversation .pb 支持

**含义：** 当前来源支持已知 SQLite conversation .db；Antigravity 的主 conversation .pb 仍处于不支持边界。现有附属 metadata 的 protobuf 过滤代码不等于完整 .pb 用量采集已经支持。

**例子：** 一台机器只有 .pb，没有已支持的 .db，应用应提示格式不支持或覆盖限制；后续要证明其中确实存在足够的 usage 字段，才能统计。

**完成标准：** 明确真实 schema/版本、token 包含关系、时间/会话身份、损坏/缺失字段与最小 fixture；仅提取必要用量元数据，不保存正文/认证内容。不能把 parser “读得开二进制”当成统计正确；两平台采集/隐私/失败保留历史验证通过后再改变能力宣传。

<a id="t14"></a>
## T14：订阅额度、重置时间与配额

**含义：** 使用量统计与账户订阅限额是两类数据。现有 token 和 API 等价成本不能直接推导“Plus/Pro 还剩多少额度”。

**例子：** 产品可能按消息、计算资源或滚动窗口限制，不同模型/账户的限制也不同；同样的 token 数不一定消耗相同订阅额度。

**完成标准：** 有可信且获授权的账户级来源，记录额度单位、窗口、重置时区、更新时间与缺失/过期状态；和 usage 展示分开，不可靠时显示不可用。三个来源 supportsQuota 当前均为 false，不凭订阅价格或估算 token 编造百分比。

<a id="t15"></a>
## T15：更多来源与可选同步

**含义：** ChatGPT Web、DeepSeek Harness、Cowork 等不是把品牌名加入下拉框就能支持。每个产品需要确认可获得的数据、字段含义、授权和覆盖范围。

**例子：** 网页可见正文可能只能估算 token，不能标成服务端实报；某个 Harness 的事件日志可能有真实 usage，但需确认具体仓库/版本；Cowork 的日志格式不能默认与 Claude Code 相同。

**完成标准：** 独立 Provider/Adapter、来源与精度说明、合成 fixture、用户开关和平台测试，默认不扩大读取范围。可选联网同步另行设计隐私、身份/冲突和失败策略；本机归档导入不自动变成联网同步。

<a id="t16"></a>
## T16：诊断版本与更细处理进度

**含义：** 已有任务开始/结束、检查/扫描/退避状态、错误码、native diagnostics 和归档内的采集版本。可选扩展是把可信 collector/normalization 版本及可获得的处理进度呈现在 UI；不是再次补一个已经存在的事件订阅入口。

**例子：** 排查同一来源在采集器升级前后的差异时，显示实际使用的版本，而不是只显示应用 0.0.7；如果采集器没有总文件数/进度协议，则只显示阶段，不能编造“完成 80%”。

**完成标准：** 版本来自当前采集器或对应已存快照，区分当前/历史；进度有出处和缺失状态，仍通过 UsageClient 能力协商/transport 清理。不显示原始 stderr、正文、认证信息或任意绝对路径。

## 建议执行顺序

先用现有安装包完成 **T1→T2→T3**，发现问题则修复后回归；准备长期分发时安排 **T4–T6**。P2 中可以按实际痛点选择：大日志扫描耗时优先 T7，数据安全优先 T8，跨设备使用优先 T9。每项只在其证据齐全后更新状态，不为版本号提前勾选。
